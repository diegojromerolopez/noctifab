## 1. Executive Summary & Core Directives

### 1.1 Problem Statement
During autonomous code generation runs (such as `pyedis`), execution frequently stalled or burned millions of tokens during intermediate tasks because of **premature, over-zealous linter enforcement**. Enforcing strict zero-linter rules after every atomic task prevents forward progress, forcing agents into futile repair loops over minor cosmetic or stylistic warnings before functional code even exists.

### 1.2 The Staff Engineer Directives
1. **Deterministic Auto-Formatting Without Linter Blocking**:
   - Running an auto-formatter (`FormatterCommand` executing `ruff format`, `make format`, `gofmt`, etc.) after each task is enabled as a zero-token baseline.
   - **MANDATE**: There **MUST NOT** be any rule that enforces that linters pass after individual tasks or feature user stories. Linters are strictly non-blocking advisory.
   - **Syntax Error Resilience**: If code has temporary syntax issues mid-edit, the auto-formatter fails gracefully without blocking the task pipeline.
2. **Chicago School (Classical / Detroit) Unit Testing**:
   - Unit tests must follow the Chicago school: testing real collaborating domain objects and verifying observable state transitions and return values.
   - **Anti Mock-Creep Rule**: Explicitly forbid mocking internal collaborators or asserting private method call counts (`assert mock.called_once_with`).
3. **Mandatory Dependency Injection (DI)**:
   - Dependency Injection is strictly enforced for all external, stateful, or non-deterministic boundaries (e.g., Clocks/Timers, Network Sockets, Filesystems, Subprocesses). Domain components accept injected providers (e.g., `FakeClock`, in-memory streams) to ensure 100% deterministic, race-free tests.
4. **QA Agents DoD & Comprehensive E2E Scenario Enforcement**:
   - QA Agents MUST actively ensure deliverables have high quality.
   - QA verifies that the **Definition of Done (DoD)** of the user story is completely accomplished.
   - QA mandates and verifies that **all E2E test scenarios** (happy paths, boundary conditions, error handling, exit codes, output invariants) are thoroughly authored and executed in the QA sandbox.
   - E2E harnesses for async servers/daemons must implement readiness polling (retrying connection up to 2s) and clean process teardown rather than brittle static `sleep()` calls.
5. **Mandatory Final Hardening User Story (`US-FINAL`)**:
   - Hardening, best-effort popular linter cleanup, and repository polish are deferred to a dedicated final user story (`US-FINAL: Project Hardening, Maintenance Readiness & Code Quality`).
   - Decomposed into **4 standardized atomic tasks** with hard-bounded turn ceilings and monotonicity checks.
   - **Generated by Generator Agents** and **HARD-supervised by QA Agents** leveraging the full Chicago-school unit, integration, and E2E test suite as an immovable regression safety net.

## 3. Detailed Staff Engineering Specifications

### 3.1 Chicago-School Unit Testing & Anti Mock-Creep Directives
* **Classical (Chicago) State Verification**:
  - Test real domain objects executing real algorithms.
  - Assert observable outputs, state changes, and returned data structures.
* **Negative Prompt Constraints (Stopping LLM Mock-Creep)**:
  - ❌ **STRICTLY FORBIDDEN**: Using `unittest.mock.MagicMock()`, `jest.fn()`, `gomock`, or monkey-patching on internal domain classes, structs, or collaborating services.
  - ❌ **STRICTLY FORBIDDEN**: Asserting invocation counts or internal method calls (`assert_called_with`, `assert_called_once`, `expect().toHaveBeenCalled()`).
  - ✅ **MANDATED**: Instantiate real collaborating objects with real state. Inject test doubles **only** at external/non-deterministic boundaries.
* **Enforced Dependency Injection (DI)**:
  - **Time & Scheduling**: Production classes must accept a `Clock` or `TimeProvider` interface. In tests, inject a `FakeClock` with explicit manual advancement (`clock.advance(seconds=10)`) to eliminate timing race conditions and sleep delays.
  - **I/O & Networking**: Production classes must accept stream interfaces or socket abstractions. In tests, inject in-memory buffers or loopback streams.
  - **Storage**: Production classes must accept repository interfaces. In tests, inject in-memory repository doubles.

### 3.2 QA Agent Role: DoD Enforcement & Full E2E Scenario Coverage
* **DoD Completeness Audit**:
  - The QA Agent reads the story's `Definition of Done (DoD)` and public contracts.
  - QA verifies that all public interface methods, binary paths, exit codes, and output formatting rules declared in the DoD are 100% implemented and verified.
* **Mandatory All-Scenario E2E Coverage**:
  - QA mandates that the test suite includes comprehensive black-box E2E tests covering:
    1. **Happy Paths**: Core user journeys and command workflows.
    2. **Error Invariants**: Proper exit codes (non-zero), formatted stderr messages, and rejection of malformed inputs.
    3. **Edge Cases**: Empty inputs, large payloads, boundary limits, and unexpected arguments.
  - QA executes these scenarios in the isolated QA sandbox (`HostQASandboxRunner` / `DockerQASandboxRunner`).
  - If any scenario is missing from the test suite or fails in the sandbox, QA blocks the merge (`ReviewRejected`) and requires remediation.
* **Daemon / Server Lifecycle Robustness**:
  - E2E harnesses must never use hardcoded static `sleep()` delays to wait for server initialization.
  - E2E runners must implement **readiness polling** (retrying ping/socket connect up to 2 seconds with exponential backoff).
  - All test runners must trap exit signals to kill background subprocesses cleanly (`trap 'kill $PID 2>/dev/null' EXIT`).

### 3.3 Linter Policy: Auto-Formatters Allowed, No Blocking Linter Rules
* **Auto-Formatter Execution**: `FormatterCommand` runs deterministically after every task to format source and test files.
* **Syntax Error Resilience**:
  - If the code contains a temporary syntax error during intermediate edits, the auto-formatter command failure is logged as debug and silently swallowed without failing the task or blocking the agent loop.
* **No Blocking Linter Rules**:
  - Neither feature stories nor individual tasks fail if a linter produces style/cosmetic warnings.
  - `TestValidator` evaluates task success strictly on **test execution pass/fail** (`run_tests` and E2E suites).
  - Linter feedback may be logged for informational visibility, but will never block task integration.

### 3.4 Bounded Final Hardening Story (`US-FINAL`)
* **Standardized 4-Task Decomposition**:
  1. `task-hardening-01-formatting`: Repository-wide auto-formatting, whitespace normalization, and import block sorting (1 turn, mechanical execution).
  2. `task-hardening-02-static-analysis`: Resolve Tier 1 static analysis warnings (syntax/type errors, unresolved imports) and major lint issues in production source files.
  3. `task-hardening-03-regression-verification`: Execute full test suite (`make test` + black-box E2E matrix) under QA hard-supervision to verify 0 regressions.
  4. `task-hardening-04-packaging-and-docs`: Validate entry-point scripts, executable paths, licenses, and documentation.
* **Hard Bounded Stopping Conditions (Preventing Linter Lock-in in `US-FINAL`)**:
  - **Turn Ceiling**: Maximum **2 turns** per hardening task.
  - **Monotonicity Check**: If a generator turn fails to reduce the number of linter warnings compared to the previous turn, stop remediation for that rule immediately and proceed.
  - **Linter Tolerance Budget**: Tier 1 (Blockers: syntax/type errors causing runtime crashes) must pass. Tier 2 (Advisory: style, line length, docstrings) allows a tolerance budget (e.g., ≤10-15 warnings).
