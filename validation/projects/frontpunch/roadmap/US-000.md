## User Story

As the planner,
I want a compiling Python package scaffolded with the DDD layout, the `frontpunch.configure(...)` global API, the `frontpunch.exceptions` hierarchy, and the test/docker harness in place,
So that every subsequent user story can be built on a stable, dependency-injected foundation.

## Requirements

### 1. Project Scaffold (`pyproject.toml` + DDD layout)
- `pyproject.toml` (PEP 621, hatchling backend), package name `frontpunch`, Python `>=3.10`, `[project.scripts]` `frontpunch = "frontpunch.interfaces.cli:main"`.
- DDD directory tree per SPEC §3.1:
  - `frontpunch/domain/`, `frontpunch/application/`, `frontpunch/infrastructure/valkey/`, `frontpunch/interfaces/` (with `cli/`, `http/`, `client/` subpackages).
  - Each directory has an `__init__.py` re-exporting the public symbols defined in this story.
- `frontpunch/__init__.py` re-exports `task`, `enqueue`, `configure`, `Batch` (forward-declared), and the exceptions module.

### 2. `frontpunch.configure(...)` (per SPEC §2.7)
- `frontpunch.configure(redis_url: str | None = None, encryption_key: str | None = None, dashboard_token: str | None = None) -> None`.
- Initializes a process-wide singleton client (module-level, thread-safe via a lock).
- Calling `.delay()` / `frontpunch.enqueue(...)` before `configure()` raises `frontpunch.exceptions.NotConfigured`.
- Decorators may be applied before `configure`; the client is only resolved at first enqueue.

### 3. `frontpunch.exceptions` (`frontpunch/exceptions.py`)
- `FrontpunchError` (base, subclasses `Exception`).
- `ConnectionError`, `NotConfigured`, `RateLimitExceeded`, `DecryptionError`, `SerializationError` (subclass of `TypeError`), `PauseError`.
- All subclasses have a docstring and a trivial `__init__(self, message: str = "")`.

### 4. Clock & FileSystem Ports (DI)
- `frontpunch.domain.clock.Clock` interface (`now() -> datetime`).
- A default `SystemClock` implementation in `frontpunch/infrastructure/`.
- `frontpunch.domain.fs.FileSystem` interface for testability (read/write JSON job files).

### 5. Test Harness
- `tests/unit/`, `tests/integration/`, `tests/e2e/` directories with `__init__.py`.
- `tests/e2e/docker-compose.yml` exposing Valkey on `localhost:6379/0`; E2E tests read `VALKEY_URL`.
- `Makefile` with `test` target: `coverage run --source=frontpunch -m unittest discover -s tests && coverage report --fail-under=100`.
- `ruff`, `black`, `mypy` configs in `pyproject.toml` per SPEC §3.

## Architectural & Performance Constraints
- DI: all collaborators constructor-injected; no inline instantiation of the Valkey client.
- No file exceeds 500 lines (no Python file exceeds 500 lines per AGENTS.md §2.1; this story's files are all small stubs).

## Validation Criteria

### Unit Tests
- `tests/unit/test_configure.py`: calling `enqueue(...)` before `configure()` raises `NotConfigured`; after `configure(redis_url=...)`, the singleton client is non-nil and reusable.
- `tests/unit/test_exceptions.py`: each exception subclass is importable, subclasses `FrontpunchError`, and `SerializationError` is also a `TypeError`.

### Build/Lint
- `python -m compileall frontpunch` exits 0.
- `ruff check frontpunch` exits 0.
- `black --check frontpunch` exits 0.
- `mypy frontpunch` exits 0.
- `coverage run --source=frontpunch -m unittest discover -s tests && coverage report --fail-under=100` exits 0.
